## Findings from this pass (not pre-existing known-gaps)

1. **Fixed — `LocalCascadeProvider` crashed on connect in a real browser.** `packages/voice/src/local-cascade.ts` stored the bare global `fetch` reference (`opts.fetch ?? fetch`) and called it later as `this.fetchImpl(...)`; real browsers throw `TypeError: Failed to execute 'fetch' on 'Window': Illegal invocation` because fetch's receiver check fails once detached from `window`. Never caught before because `FakeVoiceProvider` and the Node-side `voice-smoke.ts` script never exercised this code path. Fixed with `.bind(globalThis)`.
2. **Fixed — deep-linking straight to `/reader/[bookId]` or `/voice/[bookId]` (a full page load) never loaded the book.** Both screens' `loadBook` effect depended on `[bookId, loadBook]` only; `bookLocale(bookId)` resolves via the `packs` array, which is empty until `loadPacks()` finishes (an unrelated async effect, `useLibrary()`'s), so the very first call silently found no locale and never retried. Fixed by adding `packsStatus` to the effect's dependencies (both screens), and by having `useVoiceSession` call `loadPacks()` itself (the voice screen never called `useLibrary()`, so nothing else did).
3. **Fixed — voice pipeline turn latency ~27-30s, dominated by LLM prompt eval.** `apps/server/src/voice/llm.ts` never sent `cache_prompt: true` (a llama-server extension noted as a pending fixup in LEDGER 2026-09-04 18:05 but never applied); added it — cut `thinking`-state duration roughly in half in this session's runs (see the voice-live.mjs timelines).
4. **Fixed — the VAD pre-speech buffer was ~53ms in a real browser, not "a few hundred ms" as documented.** `apps/server/src/voice/session.ts`'s `PRE_BUFFER_FRAMES = 20` was a frame _count_; a real `AudioWorklet` posts one frame per ~2.7ms render quantum (vs. the 20ms frames `voice-smoke.ts` sends manually, for which 20 frames genuinely is ~400ms). Short real-mic utterances like "Guarda la palabra cigarra." were losing their first word(s) to STT. Rewrote as a duration-based buffer (`PRE_BUFFER_MS = 1200`) — confirmed fixed: `voice-live.mjs` phase A/B both transcribed the full utterance correctly after the change.
5. **Found, not fixed — voice-triggered `save_vocabulary`/`set_reading_position` can target the wrong word.** Root cause: `packages/core/src/prompt.ts`'s `buildSystemInstruction` renders the passage to the LLM as `TutorPassageSentence { id, text }` (sentence-level id + plain text only) — it never includes per-word `tokenIds`, even though the wire protocol carries them (`PassageContext.sentences[].tokenIds`, CONTRACTS §5c). The LLM has no ground truth for which literal `tokenId` string names which word, so it guesses one, and the guess can resolve to a different real word rather than failing (`apps/client/src/voice/toolContext.ts` does an exact `tokenId` lookup with no fallback). Reproduced twice, deterministically: asked to save "cigarra" in `es-fabulas-samaniego` ("Durante el verano, una cigarra canta bajo el sol."), the tutor said "cigarra" was saved both times, but the vocabulary store ended up with **"verano"** instead. This is a real, user-visible bug (the tutor's spoken confirmation doesn't match what actually happened) and is why criteria 9/10/11 above are PARTIAL rather than PASS. Flagged as a follow-up task (not fixed here — the compact-prompt-budget tradeoff needs a real design decision, not a quick patch); see the spawned task in this session's chip list.
