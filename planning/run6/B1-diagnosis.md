# B1 diagnosis: why own-provider mode did not work for Noel

Noel's three answer slots (B-1 device/context, B-2 whether Settings showed the setting saved, B-3 what the screen showed) were all blank, so per instructions all three contexts (Safari tab, Home Screen icon, desktop browser) and both save/speak orders are treated as live, and B-3 is recorded per context rather than assumed.

## 1. Ranked candidates (most likely first)

1. **Candidate 1 — storage-container mismatch** (free origin vs paid origin, or Safari tab vs Home Screen container). Most likely because it requires zero code defect, is the single most common real-world own-provider failure shape, and both origins already offer the same Settings screen (VERIFIED, `apps/client/app/profile.tsx:173,232-237`), making a save-on-one/test-on-the-other mistake easy and silent.
2. **Candidate 5 — not a code defect** (validation reachable-but-rejected, unbilled account, or the paste never completed). Second because the recovery-panel path for a *pre-session* failure is a clear, working, single-string error (VERIFIED `openai-key.tsx:63`) that would leave an obvious paper trail if Noel remembered seeing it, and Noel's own words ("haven't been able to try") are equally consistent with "never finished saving."
3. **Candidate 4 — standalone (Home Screen) permission gap**. Third because it is the leading hypothesis already carried in `planning/LEDGER.md` since Run 4 and is the one candidate that cannot be ruled out by static code reading at all — only a device test resolves it — so it stays plausible until B-1/B-3 pin down that Noel actually used the Home Screen icon.
4. **Candidate 3 — dead-end failure UI**. Fourth: it explains why Noel would give up (no BYOK button, no fix-mic link in the mid-session `isBroken` panel) but only fires *after* candidates 1/2/4 already got him to a live session attempt — it's a "why he stopped trying," not a "why it failed" candidate.
5. **Candidate 2 — no user gesture at capture time**. Ranked last because on iOS Safari a *missing* permission prompt (never having been asked before) does not require a gesture to fire the browser's native permission dialog the first time; gesture-timing issues typically manifest as a *silently rejected* getUserMedia after the user has already denied/dismissed a prior prompt, which is a narrower and less likely first-time failure than 1/2/4/3.

## 2. Candidate sections

### Candidate 1 — storage is per origin and per container
- **What Noel would have seen:** Settings → "Your OpenAI key" shows *no* stored key ("A key is stored on this device" text absent) on whichever origin/container he is currently in, even though he remembers saving one — because he saved it on a different origin or a different install container.
- **Code, VERIFIED:**
  - `apps/client/src/voice/byokKey.ts:24` — one storage key name, `BYOK_STORAGE_KEY = 'sotto.byok.openaiKey'`, written via `webStorage()` (line 32-40, plain `localStorage`) with no cross-origin sync anywhere in the file.
  - `apps/client/src/voice/availability.ts:60-62` — `byokPathUsable()` only calls `hasByokKey()`; presence-only check, no mic-permission check, so an *absent* key routes silently to whatever else is available (§3 below), not to any "key missing" message.
  - `apps/client/app/profile.tsx:173,232-237` — the BYOK row sits in the unconditional "Tutor" group, so both the free origin and the paid origin offer `/settings/openai-key`, each with its own `localStorage`.
  - iOS Home Screen installs use a separate WebKit storage container from the same URL opened in a Safari tab — this is standard WebKit behavior (`localStorage` is scoped to the web-app's install container, distinct from the browser-tab container for the same origin), not something this repo's code controls or could check; noted as INFERRED (platform behavior, not read from this repo) but well-established WebKit behavior, not a guess about this app specifically.
- **B-1/B-2/B-3 discriminator:** B-1 (which origin/context) + B-2 (did Settings show "saved" *on the exact device/context he later spoke from*) together rule this in or out. If B-2 is "yes, saved" on the *same* context he spoke from, candidate 1 is ruled out for that attempt.

- **Minimal reproduction step:** save a throwaway marker value under a differently-named key in `localStorage` (never the real `sotto.byok.openaiKey` name) on origin A / context A, then check for it on origin B and on the Home Screen container for the same origin — see B2 recipe step 7.

### Candidate 2 — no user gesture at capture time
- **What Noel would have seen:** tapping "Talk to the tutor" navigates to the voice screen normally (no visible error), then either nothing happens (session never reaches a listening state) or the same `mic_unavailable`/"Microphone unavailable" panel from Candidate 3 appears, but *because* `getUserMedia` was called outside a tap rather than because permission was actually denied.

  - `packages/voice/src/transports/web-audio.ts:61-90` — `getUserMedia` (line 66) and `new AudioContext()` (line 69) execute inside `startCapture()`, called from `provider.connect()` (`openai-direct/provider.ts:144-156`), itself invoked from the effect above — confirmed no synchronous call chain back to a tap.

## 3. What B2 can discriminate

A simulator reproduction run with **no setting value present at all** cannot exercise the own-provider path in the first place: `apps/client/src/voice/availability.ts:60-62` (`byokPathUsable()` returns `hasByokKey()`) will be `false`, so none of the `byokUsable` branches in `resolveAvailability` (lines 128-160) are reachable — every one of Candidates 2, 3, 4 lives inside code paths gated on a stored key existing. B2-without-a-key can therefore only usefully test Candidate 1 (storage-container behavior itself, using a throwaway marker key, not the real one) and confirm which *other* provider the gate falls back to.

- **Serving `pnpm serve:web` (a static export, no `apps/server` running) with no key:** `health` is `null` (VERIFIED `availability.ts:66`, `availabilityFromHealth` returns `{status:'unavailable', reason:'server'}` when `health` is null), `cloudUsable` false (no signed-in paid entitlement locally), so the gate falls through local (unavailable) → byok (`byokUsable` false, skipped, line 143) → `browserAvailability()` (line 147) → WebGPU-model path if available, else the `needs-download`/`no-webgpu` panel (the `panelState` branch, `[bookId].tsx:287-315`, which *does* show the "Use your own key" button — but only because the gate failed to find anything else, not because the own-provider path itself ran).
- **With `apps/server` running and no key:** `health` is non-null; if all three services (`stt`,`llm`,`tts`) report healthy, `availabilityFromHealth` returns `{status:'ready', path:'local'}` (line 73) and the gate picks the **local** provider outright (line 134-138) before ever reaching the byok branches — own-provider mode is not exercised at all in this configuration either.
- **Conclusion:** to reproduce anything about *why own-provider mode itself* fails (Candidates 2, 3, 4), the simulator run must actually save a real key through Settings first. The no-key run is only useful for Candidate 1's storage-container check and for confirming the fallback provider identity above.
